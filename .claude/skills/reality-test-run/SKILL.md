# Reality Test run

Rules: §4, §5, §6C/D, §7, §13 and §16. **The results must be generated by the submitted system. Never hand-edit or replace an agent output** (doing so fabricates results and can zero the component or disqualify the team). The code is already frozen at 16:30, so don't change the implementation in this window. If the runner crashes on a case, re-running the same code is fine. Patching the code is not. Converting the *input* into a format the frozen loader reads (section "Step 5") is allowed: it changes no code and the conversion script is part of the submitted repo.

Clock for the window (BST): 16:30 unpack · 16:35 triage decided · **16:37 run started** (16:45 at the latest if converting) · 16:50 time fallback · 16:55 commit and push · 17:00 freeze.

Every step below is a command with an exact pass signal. Run them from the repo root. Set these two variables once and reuse them:

```bash
RELEASE="HackatonChallendges"                      # whatever the organisers' folder is called after unpacking
CASES="$RELEASE/Property Management"               # the folder whose children are the case folders; fix in Step 1
```

## Before 16:30 (rehearse at least once)

- `.env` is filled in, and `pnpm verify` passes.
- The code and demo video are committed and pushed, and the hash is noted (the 16:30 form).
- Time a full practice batch to confirm that N cases fit in about 15 minutes. Adjust `--concurrency`. If the run hits rate limits, set `LLM_CONCURRENCY` in `.env` to cap in-flight requests per model.
- Run the probe on the public examples so you know what a green result looks like:
  ```bash
  pnpm exec tsx .claude/skills/reality-test-run/scripts/convert-to-organiser.ts --probe "HackatonPublicCases/Property Management"
  ```
  Pass: last lines read `PROBE OK: 50/50 cases load` and `--at 100%`. (The probe prints counts only, never case text, so it is safe on the holdout cases.)
- Run the converter's test so the fallback is known-good: `pnpm test -- convert-to-organiser` passes 8 tests.
- Rehearsal numbers recorded in the section "Rehearsal record" below.

## At 16:30: format triage (5 minutes, 16:30–16:35)

Goal: pick one of four paths and the `--at` flag, without reading case content. The decision table is at the end of this section. Don't read cases to steer the agent; `ls`, `head -5` and counts are enough.

### Step 0 (16:30). Unpack and note the time

```bash
date "+%H:%M"
unzip -q -o <download>.zip -d . 2>/dev/null; ls
```
Pass: the released folder exists at the repo root (set `RELEASE` to its name). It is **not** `HackatonPublicCases/`.

### Step 1 (16:31). Layout census: where are the case folders?

```bash
find "$RELEASE" -maxdepth 3 -type d | head -40
find "$RELEASE" -type f | sed 's#.*/##' | sed 's#.*\.##' | sort | uniq -c | sort -rn | head   # extension histogram
```
Pass: you can name the folder whose immediate children are the cases. Set `CASES` to it (for the organiser layout this is `$RELEASE/Property Management` or `$RELEASE` itself if the track level is missing). Then:

```bash
N=$(find "$CASES" -mindepth 1 -maxdepth 1 -type d | wc -l | tr -d ' '); echo "cases: $N"
```
Pass: `N` is between 1 and 60. If `N` is 0 the cases are single files, not folders: go to Step 5 with `--flat`.

### Step 2 (16:32). Organiser format? (`index.md` + `history.md` [+ `attachments/`], loaded by `src/agent/publicCases.ts`)

```bash
echo "index: $(find "$CASES" -mindepth 2 -maxdepth 2 -name index.md | wc -l | tr -d ' ')  history: $(find "$CASES" -mindepth 2 -maxdepth 2 -name history.md | wc -l | tr -d ' ')  of $N"
grep -c '<a id="event-' "$CASES"/*/history.md | head -5
```
Pass: both counts equal `N`, and every `history.md` has at least one `<a id="event-` anchor. Then run the probe (Step 4) and go to the run. If only some cases match, the folder is mixed: run the matching ones with `--only` and convert the rest (Step 5).

### Step 3 (16:32). Our practice format? (`case.md` + `inputs/`, loaded by `src/agent/cases.ts`)

```bash
echo "case.md: $(find "$CASES" -mindepth 2 -maxdepth 2 -name case.md | wc -l | tr -d ' ') of $N"
```
Pass: equals `N`. The generic loader also accepts any folder of files per case without a `case.md` (every file becomes an input, the brief is empty). That is a *working* fallback but a weak one, because the agent then gets no task section and no event order. Decide with the probe in Step 4: if the probe says "no brief file", convert (Step 5) rather than run bare.

### Step 4 (16:33). Probe: does the frozen loader read every case? Which `--at`?

```bash
pnpm exec tsx .claude/skills/reality-test-run/scripts/convert-to-organiser.ts --probe "$CASES"
```
Pass: `PROBE OK: N/N cases load`, plus one recommendation line:
- `--at 100%`: the histories end at the decision point (no `Recorded action` marker). Use `--at 100%`. **Never run the Reality Test with the default `--at auto` in this situation: with no marker, `auto` hides the second half of every history.**
- `--at auto`: every `index.md` carries a `Recorded action: [History event NNN]` marker, so the loader cuts just before it and hides the ending sections. Use `--at auto`.
- `MIXED`: run the two groups separately with `--only`, each with its flag.
- `FAIL` with `✗ <id>: <reason>` lines: those cases need Step 5, the rest can run as-is with `--only`.

### Step 5 (16:33–16:45). Third format: convert to organiser format, 10-minute cap

The script turns a folder of loose files per case (`.eml`, `.txt`, `.md`, `.json`, `.html`, plus PDFs and images as attachments) into `index.md` + `history.md` + `attachments/` in the shape the parser needs. It splits thread dumps on `From:` blocks, headings or `---` rules, orders events by any date it finds, and never invents a date, party or attachment (undated events read `date unknown`).

```bash
pnpm exec tsx .claude/skills/reality-test-run/scripts/convert-to-organiser.ts --in "$CASES" --dry-run | head -60
```
Pass: one line per case with a plausible event count, and no case with `0 events` and `0 attachments`. Then write and verify in one go:

```bash
pnpm exec tsx .claude/skills/reality-test-run/scripts/convert-to-organiser.ts --in "$CASES" --out cases/reality-converted --check
CASES=cases/reality-converted
```
Pass: `Wrote N case(s)` and `PROBE OK: N/N` and `--at 100%`. Single files per case: add `--flat`. The converted folder (`cases/reality-converted`, not `runs/`, which is git-ignored) is committed with `ANSWERS/` so the run is reproducible.

If 16:45 arrives and the probe is still red: **stop converting**. Run the raw `$CASES` through the generic loader (Step 3 fallback) so every case still gets an answer. Coverage is scored; polish is not.

### Step 6 (16:33, in parallel). Supplied API or MCP toolset?

```bash
ls "$RELEASE" | grep -iE 'api|mcp|openapi|swagger|tool|\.json$|\.yaml$'
grep -rilE 'https?://|api[_ -]?key|bearer|token|mcp' "$RELEASE"/*.md "$RELEASE"/README* 2>/dev/null
```
Pass for "no toolset": the second command prints nothing (a plain `README.md` in the first listing is normal; `head -40` it). Then the mock toolset is the acting surface and the ledger is the evidence, which is the master plan's assumption.

If an HTTP tool API URL (and maybe a key) is supplied: set `ORGANISER_API_URL` (and `ORGANISER_API_KEY`) in `.env`; that is configuration, not a code change. If its tool names, routes or argument names differ from ours, `ORGANISER_TOOL_MAP` renames them (JSON, see `.env.example`); if it needs more than renames, or is MCP over stdio, leave the variables empty and run on the mock. The run's second line reads `Toolset: organiser API at <host> (http), K of 28 tools mapped`. Pass signal: in the first finished case, `grep '^Toolset' ANSWERS/<id>/REASONING.md` names the organiser API, and `grep -c '"verified"' ANSWERS/<id>/trace.jsonl` is ≥ 1. No manual fallback is needed: the first failure (network, timeout, HTTP ≥ 400, non-JSON) switches the whole run to the mock, and every affected REASONING says so in its `Toolset:` line.

### Decision table (16:35)

| Signals | Path | Run flags |
|---|---|---|
| Step 2 counts = N, probe OK, `--at 100%` recommended | Organiser format, histories end at the decision point | `--in "$CASES" --at 100%` |
| Step 2 counts = N, probe OK, `--at auto` recommended | Organiser format with recorded-action markers | `--in "$CASES" --at auto` |
| Step 3 count = N, probe OK, briefs present | Practice format | `--in "$CASES"` |
| Probe OK but "no brief file", or probe FAIL, or N = 0 | Third format: Step 5 | `--in runs/reality-converted --at 100%` |
| Step 6 finds an HTTP tool API | Any of the above plus `ORGANISER_API_URL` (and `ORGANISER_API_KEY`, `ORGANISER_TOOL_MAP`) in `.env` | as above |

## At 16:37: run

1. Run everything in one go, with the flags from the decision table:
   ```bash
   mkdir -p ANSWERS
   pnpm cases --in "$CASES" --out ANSWERS --at 100% --concurrency 6 --deadline 16:50 --critic off 2>&1 | tee ANSWERS/run.log
   ```
   Replace `--at 100%` with the probe's recommendation, and `--concurrency 6` with the rehearsal's recommendation (Rehearsal record below). Keep `--critic off` explicit: the M3 A/B shipped the critic off, and the flag overrides a stray `CRITIC=on` left in `.env` (the start line names the critic model only when it is on). (`*.log` is git-ignored, so the log stays local; the per-case `trace.jsonl` is the committed evidence.) `--deadline 16:50` makes the run finish by 16:50 whatever happens: per-case timeouts shrink as the deadline approaches (the start line prints the deadline and the case timeout), a case still running at its timeout writes the agent's fallback answer with its verified ledger, and a case that can no longer start gets an honest "not processed within the run's time budget, escalated (system failure)" answer. Nobody needs to press Ctrl-C.
2. Watch the log: each finished case prints `✓ <id> <outcome> (<s>s, $<cost>)`. Pass at the end: `decisions N/N · resumed 0 · budget-skipped 0` on the `Done in` line and no `CRASH`, `NO DECISION` or `BUDGET SKIP` row in the table. The next line reads `Rate-limit retries: <total> across <cases> cases (max <m> in one case) at concurrency <c> · next run: <advice>`; use its advice for any re-run.
3. If some cases crashed, timed out or were budget-skipped and there is time left (before about 16:48), re-run the **same command plus `--resume`**. Never re-run into `ANSWERS` without `--resume`: every case would start again and, close to the deadline, decided answers get overwritten with `BUDGET SKIP`. Use the same command plus `--resume`, with the advised `--concurrency` and a new `--deadline` (for example 16:53), appending to the log (`tee -a`). `--resume` keeps every case that already has a decided `result.json` (byte-identical) and re-runs only the rest; the start line says `resuming K of N`. If a case still fails, **leave the failure in ANSWERS**, since an honest failure record is better than a fabricated answer. The runner writes the "escalated (system failure)" pair itself.
4. **16:50 time fallback.** Nothing to do by hand: `--deadline` has already written an answer for every case. If the process was killed (laptop, terminal), `--resume` with a new `--deadline` fills only the gaps. Ctrl-C once also stops cleanly (running cases get the fallback answer, unstarted ones are skipped, exit code 130); twice exits at once. Never write the files by hand.
5. Verify:
   ```bash
   bash .claude/skills/submission-check/scripts/check.sh
   ls ANSWERS | wc -l; find ANSWERS -name ANSWER.md | wc -l; find ANSWERS -name REASONING.md | wc -l
   pnpm checks --cases "$CASES" --answers ANSWERS | tail -1
   ```
   Pass: the three counts are equal to N, and the last line reads `Checks: N case(s) evaluated · 0 critical/prohibited failure(s)`. `pnpm checks` is read-only (no `--write`, no API key) and runs the deterministic checks (cited ids exist, case questions answered). If it reports a failure, leave ANSWERS as they are (hand edits are forbidden) and note it for the demo. Spot-read 2-3 for formatting only, not content edits.
6. **By 16:55**, commit and push:
   ```bash
   git add ANSWERS cases/reality-converted 2>/dev/null; git commit -m "chore: reality test results" && git push
   git rev-parse HEAD
   ```
   Put the hash in `SUBMISSION.md` and on the form. Ask the user before pushing to `main` if that's the submission branch.

## After 17:00

The implementation and ANSWERS must not change. Only these may be added: the demo video (via Git LFS), the LinkedIn and X post URLs, and SUBMISSION.md metadata (team, track, members, hash, video path). Make sure the repo is **public**. Run `submission-check` one last time.

## Runner flags

`src/run.ts`: `--in --out --only --at --concurrency --timeout --model --thinking --chaos --seed`, plus:

- `--critic on|off` (needs the value; a bare `--critic` is an error). Defaults to `$CRITIC`, else `off`.

- `--deadline HH:MM` (local time today) and/or `--budget-min M` (minutes from start); the earlier wins. The run exits 1 if the deadline has passed or is more than 3 hours away. Per-case timeout: `min(--timeout, max(90 s, 2 × budget × concurrency / N))`, clamped to the time left minus 20 s; a case is not started with under 60 s left.
- `--resume`: keep cases whose folder has `ANSWER.md`, `REASONING.md` and a decided `result.json` (not crashed, not skipped); re-run the rest. Off by default.
- Ctrl-C: once for a clean stop, twice to exit at once.
